# Unity Project Setup Reference

Detailed guidance for the `bootstrap` skill. Read this when actually
configuring a Unity project; the skill itself only carries the outline.

## 1. Editor settings that must be verified first

These two settings make a Unity project diffable and mergeable. Without them,
git collaboration and AI-assisted review are effectively impossible.

| Setting | Location | Required value | Why |
|---|---|---|---|
| Asset Serialization | Edit → Project Settings → Editor → Asset Serialization | **Force Text** | Scenes/prefabs become YAML text; git diffs and conflict resolution work |
| Version Control Mode | same page | **Visible Meta Files** | `.meta` files (asset GUIDs) are committed; references survive across machines |

Check them by reading `ProjectSettings/EditorSettings.asset`
(`m_SerializationMode: 2` = Force Text, `m_ExternalVersionControlSupport:
Visible Meta Files`). Reading this file is fine — **writing** it should go
through the Editor UI or an Editor script.

## 2. Git configuration

Use `templates/unity/gitignore-unity.txt` as the project `.gitignore`. Key
points people get wrong:

- `Library/`, `Temp/`, `Obj/`, `Logs/`, `UserSettings/` are regenerated — never commit.
- `*.csproj`, `*.sln` are IDE artifacts regenerated by Unity — ignore them.
- **Do commit** `ProjectSettings/`, `Packages/manifest.json`, and
  `Packages/packages-lock.json` — they define the project.
- Consider `git lfs` for large binaries (textures, audio, fbx) only when they
  actually appear; a primitive-based First Playable usually needs none.

## 3. asmdef architecture (Standard mode)

Assembly definitions exist for two reasons here: **compile-time dependency
enforcement** and **fast, engine-free tests**.

```text
Game.Core           ← pure C#. noEngineReferences: true. The game's rules live here.
   ↑
Game.Gameplay       ← MonoBehaviours, physics, scene glue. References Core.
   ↑
Game.Presentation   ← camera, UI, VFX, audio. References Core + Gameplay.

Game.Infrastructure ← save/load, services. References Core only.
Game.Editor         ← editor tooling. Editor platform only.
Game.Tests.EditMode ← tests for Core (and pure parts of Gameplay).
Game.Tests.PlayMode ← runtime behavior tests.
```

Dependency rule: arrows point downward only. `Core` referencing `Gameplay` is
always a mistake — it makes rules untestable without the engine.

Ready-made asmdef JSON files are in `templates/unity/`. The critical one is
`Game.Core.asmdef` with `"noEngineReferences": true` — this is what forces the
humble-object split that makes EditMode testing trivial (see
`unity-testing.md`).

In **Prototype mode**, use a single `Game.asmdef` plus the two test asmdefs.
Don't skip the test asmdefs even in jams — they cost nothing and Test Runner
won't see tests without them.

## 4. Packages

Check `Packages/manifest.json` before proposing installs. Typical First
Playable set for Unity 6:

| Package | ID | Note |
|---|---|---|
| Input System | `com.unity.inputsystem` | Prefer over legacy Input; check Player Settings → Active Input Handling |
| Test Framework | `com.unity.test-framework` | Usually present by default |
| Cinemachine | `com.unity.cinemachine` | Only if the design needs camera work (v3.x on Unity 6 — namespace is `Unity.Cinemachine`) |
| URP | `com.unity.render-pipelines.universal` | Don't switch pipelines on an existing project without an explicit decision record |

Never remove packages during bootstrap. If a package looks unused, list it in
the report and let the user decide.

## 5. Scenes

| Scene | Purpose | Contents at bootstrap |
|---|---|---|
| `Bootstrap` | entry point, service init | empty GameObject `AppRoot` |
| `FirstPlayable` | the playable core loop | ground plane + player placeholder |
| `Sandbox` | isolated feature experiments | ground plane |
| `Test` | manual/automated verification | empty |

Create scenes via Unity MCP or an Editor script (`EditorSceneManager.NewScene`
+ `SaveScene`) — never by writing `.unity` YAML by hand. If MCP is not
connected, generate a one-shot Editor script under `Assets/_Game/Scripts/Editor/`
and instruct the user to run it from the Unity menu, then verify the scenes
exist.

## 6. Idempotency checklist for bootstrap

Before creating anything, build a table: item → exists? → action
(create / skip / propose-merge). Rules:

- Existing folder with content → skip, report.
- Existing `CLAUDE.md` → show a merged diff, never overwrite.
- Existing asmdefs anywhere under `Assets/` → do NOT add overlapping asmdefs;
  report the existing assembly map instead and adapt names.
- Existing scenes with the target names → skip, report.
- Second run of bootstrap on a clean result → must produce zero changes.
